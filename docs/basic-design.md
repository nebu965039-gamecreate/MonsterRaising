# ドット絵モンスター育成ウィジェットアプリ 基本設計書

version: 0.1(初版・アジャイル運用前提のたたき台)

---

## 1. プロジェクト概要

### 1.1 コンセプト
スマートフォンのホーム画面ウィジェットに常駐するドット絵モンスターを、お世話・ミニゲームを通じて育成するアプリ。フレンドとの緩い非同期交流を持つ。

### 1.2 プラットフォーム方針
- **初回リリース**:Android(ネイティブ、Kotlin)
- **将来対応**:iOS版(初回リリース後に着手)。**Kotlin Multiplatform(KMP)でロジック層のみを共有する方針で確定**(詳細は1.2.1節)
- **初回運用**:自分+友人内でのクローズド運用 → バランス調整後、広告実装の上で一般リリース

#### 1.2.1 iOS版着手時のロジック共通化方針(確定)
- **KMPで共有する部分**:UIやプラットフォーム固有APIに依存しない純粋な計算ロジックのみ
  - ステータス減少計算(オフライン経過時間ベース、4.1節)
  - 進化条件のスナップショット判定(4.3節)
  - 各ミニゲームのスコア計算・クリア判定ロジック
  - 装備効果・有効度の計算式
- **共有せず、プラットフォームごとにネイティブ実装する部分**:
  - 画面UI(Android:Jetpack Compose / iOS:SwiftUI)
  - ウィジェット(Android:RemoteViews・Glance / iOS:WidgetKit。仕組みが異なるため共有不可)
  - ドラッグ&ドロップ・スワイプ等のジェスチャー処理(10.2.1節・10.2.2節)
  - Firebase SDKまわりの薄いラッパー部分
- **Android実装時の準備**:iOS着手はロードマップ上まだ先だが、Android側の計算ロジック(ステータス計算・進化判定・スコア計算)は、UIやAndroid固有APIから切り離した独立クラス・関数として実装しておく。これにより、iOS着手時にKMPの`commonMain`へ移しやすくなる。現時点でKMP構成そのものを組み込む必要はない

### 1.3 開発体制
- Claude Codeを用いたアジャイル開発。本書は初期の基本設計書であり、実装を進めながら随時更新する前提(生きたドキュメント)

### 2.1 通信方針
リアルタイム対戦・リアルタイム同期は行わない。すべて「都度フェッチ+ローカル演出」の非同期設計とし、サーバー費用と実装難易度を抑える。

### 2.2 リワード広告の運用方針
- 各ミニゲーム(落ち物パズル/カード×NPC戦/壁破りゲーム)の1日のプレイ回数上限:3回(ミニゲームごとに独立してカウント)
- リワード広告を1回視聴するごとに、対象ミニゲームのプレイ回数を+1回追加できる
- 広告によるプレイ回数追加の1日あたりの上限:2回(叩き台。合計最大5回/日/ゲームとなる想定。バランス調整で変更可)
- 追加回数はミニゲームごとに独立してカウントする(あるゲームで広告視聴しても他のゲームの回数には影響しない)
- プレイ回数上限に達した際は、リワード広告の視聴とミニゲーム券(8.4節、探索で入手)の使用のどちらかをプレイヤーが選択できる
- **実装上の取り決め(暫定を含む。`MiniGameConfig`)**:
  - 回数は、プレイを開始した時点で 1 つ消費する(途中でやめても戻らない)
  - 日付は端末の現地時間で、0 時に切り替わる(確定)。広告・ミニゲーム券による追加分も、日付が変わるとリセットされる
  - ミニゲーム券は、どのミニゲームでも使える共通の券とする(確定。使ったゲームの回数が +1 される)
  - 広告(Phase 8 で実装)ができるまでは、デモ用のボタンで広告なしに 1 回追加できる
  - ミニゲームで得られる有効度には 1 日の上限を設ける(5.4節)。知力系・筋力系それぞれ、全ミニゲーム合計で 1 日 60(確定)。上限で削られた分は反映されず、機嫌は対象外
  - 1 プレイで得られる有効度の目安:落ち物パズルは `floor(スコア÷100)` を知力系・筋力系の両方に(上限なし。目標 1500 点で各 +15)、カード×NPC戦は知力系のみ(勝利で +8〜+16、無効試合 +1)。どちらも 1 日の上限で頭打ちになる
  - クリア報酬(8.5節)はクリアのたびに付与する。装備アイテムは上級の初回クリア時のみ

## 3. キャラクター表現の仕組み

### 3.1 アニメーション方式
**差分画像切り替え方式**を採用。パーツ単位でリアルタイム合成するのではなく、状態ごとに完成形の静止画を用意し、切り替えて表示する。

- 理由:ウィジェット(RemoteViews/Glance)はリアルタイムな複雑合成に不向きなため
- 本体アプリ側もウィジェットとの資産共有のため同方式に統一

### 3.2 パーツ構成(アセット制作用の分割単位)
頭(目・口統合、顎は独立させず差分画像内で表現)/胴体/右腕/左腕/右足/左足/尻尾/背中 の8パーツ。

### 3.3 解像度・表示仕様
- **内部解像度**:48×48px
- **表示倍率**:整数倍(5倍=240px等)を基本とし、拡大時のジャギー・滲みを防止
- **画角**:正面〜斜め前寄りのシンメトリー構成(実素材のサンプルに準拠)

### 3.4 フレーム構成(最低限のセット)
| フレームキー | 用途 |
|---|---|
| normal(idle) | 通常時の待機 |
| walk(walk / walk_mid / walk_a / walk_b) | 移動演出用。walk は元の歩行ポーズ(素材)、walk_mid は手前・奥の脚4本すべてを同じ高さで接地させた基本ポーズ。walk_a・walk_b は4本の脚を前後に斜め(手前の前足+奥の後ろ足 / 手前の後ろ足+奥の前足)の逆位相で振った2枚で、頭を1px下げる。walk_a → walk_mid → walk_b → walk_mid の順で繰り返し、脚を交互に振り頭が上下する歩行にする |
| happy | なでた時、ミニゲームで良い結果が出た時 |
| sad | ステータス低下時の表情 |
| attack | ミニゲームの応援演出、食事のリーチ動作等に転用可 |
| damage | ミニゲームのダメージ演出、体調不良時 |
| eat(eat_1 / eat_2) | 餌やり時の食事アニメーション(10.2.1節)。口元に餌を持った状態と齧った状態の2枚 |
| dirty | 清潔度0の専用フレーム(煤+アホ毛。4.6節・10.2.2節) |
| idle_up | idleの揺れ用。normalから頭・胴体・尻尾を1px上げ、足元は固定したフレーム |
| run / jump | 将来のミニゲーム演出用に予約 |

**idleの動き**:idleは `normal` と `idle_up` の2枚を交互に表示する微小な上下の揺れで表現する。`idle_up` は、頭・胴体・尻尾を1ピクセル(元画像単位)上げ、足元は固定した完成済みの差分フレームとする(パーツのリアルタイム合成はしない。3.1節の方針どおり)。`walk` は移動演出用とし、idleでは使わない。なお、フレーム定義には表示位置のオフセット `dx` / `dy` も指定できる(画像全体を動かしたい演出用)。

### 3.5 著作権に関する留意事項
既存キャラクター(たまごっち・デジモン等)のシルエット・配色・UIモチーフ・効果音・名称は使用しない。ゲームメカニクス(お世話→進化という仕組み自体)は使用して問題ない。

## 4. 育成機能 詳細設計

### 4.1 ステータス定義

| ステータス | 範囲 | 増加要因 | 減少要因 |
|---|---|---|---|
| 満腹度 | 0〜100 | 餌やり(+20〜30/回) | 時間経過で自動減少(10分ごとに-1。-6/時間) |
| 清潔度 | 0〜100 | 掃除(汚れ1箇所を落とすごとに+20。10.2.2節) | 時間経過で自動減少(10分ごとに-1。-6/時間) |
| 機嫌 | 0〜100 | なでる(+10)、餌やり(+5。暫定)、ミニゲームプレイ(+5〜15、成績に応じ変動) | 満腹度・清潔度のどちらかが60を下回っている間、時間経過で-5/時間 |
| 有効度(知力系) | 累積値、上限なし(進化判定は閾値方式) | 落ち物パズル(バランス型、5節)・カード×NPC戦(6節)の成績に応じて加算(1日の獲得上限あり) | 減少しない |
| 有効度(筋力系) | 累積値、上限なし | 落ち物パズル(バランス型、5節)・壁破りゲーム(7節)の成績に応じて加算(1日の獲得上限あり) | 減少しない |

度胸系有効度は廃止し、ベースとなる有効度は知力系・筋力系の2軸とする。落ち物パズルは知力系・筋力系の両方を均等に獲得できる「バランス型」とし、カード×NPC戦は知力系専門、壁破りゲームは筋力系専門とすることで、知力2ルート・筋力1ルートという偏りを解消する。

減少はローカル端末で「前回起動時刻からの経過時間」を基に一括計算するオフライン計算方式とする(常駐プロセスは持たない)。長時間放置時の急激な低下を避けるため、経過時間の上限(24時間分でキャップ)を設ける。減少速度は、満腹度・清潔度とも満タンから上限より前(約17時間)に0へ届くように設定する。これにより上限が働く時点では下限に達しており、上限は最終的な値に影響しない(この方針を保つこと)。なお上限は減少量にだけ効き、4.4節の「0が24時間継続」などの継続時間は実際の時刻で数える。

### 4.2 お世話アクション

| アクション | 実行場所 | 効果 | 制限 |
|---|---|---|---|
| 餌やり | ウィジェット/本体アプリ | 満腹度+、機嫌+ | クールダウン(例:30分に1回)、または累積で効果逓減 |
| 掃除 | 本体アプリ(ウィジェットは簡易版のみ) | 清潔度+ | 同上 |
| なでる | ウィジェット/本体アプリ | 機嫌+、演出発火 | クールダウンなし(頻度は演出の飽き対策で緩やかに制限) |
| ミニゲームで遊ぶ | 本体アプリ | 機嫌+、対応する有効度+ | 1日の有効度獲得上限あり |

### 4.3 進化設計

**段階と期間**:卵 → 幼年期 → 成長期Ⅰ → 成長期Ⅱ → 成熟期(成熟期でルート分岐)

| 段階 | 期間 | 卵からの累積目安 |
|---|---|---|
| 卵 | 1分 | 1分 |
| 幼年期 | 1日 | 約1日 |
| 成長期Ⅰ | 3日 | 約4日 |
| 成長期Ⅱ | 1週間 | 約11日 |
| 成熟期 | 2週間 | 約25日 |

成長期Ⅰ・成長期Ⅱは見た目を完全に一新する(段階内での細かい差分演出は設けない)。

**分岐ルート(通常)**:
- 知力ルート:知力系有効度が筋力系を上回っている場合
- 筋力ルート:筋力系有効度が知力系を上回っている場合

**分岐ルート(特別・レア)**:
以下はいずれも通常ルートとは別枠の、レアな進化として位置づける。複数の条件が同時に成立した場合は優先順位を設けず、進化のタイミングでプレイヤーがどの進化先にするかを選択できるようにする(選択UIを表示する)
- 天候ルート:特定の天候での累積ケア回数が閾値を超えた場合に解放(4.8節)
- アイテムルート:ミニゲームクリア報酬・探索で入手した特定アイテムを、進化時に所持している場合に解放(5.4節・6.5節・7.5節・8節)
  - 桜吹雪(4.8節、4/1〜4/15の期間限定演出)の期間中は、キャラクターからのプレゼント演出(10.2.3節)を通じて期間限定の特別なアイテムを配布し、そのアイテムを所持している場合はアイテムルートとして扱う
- フレンドルート:フレンドシップポイント(9節)が一定値を超えている場合に解放。2段階のレア進化を想定(例:10,000Pで解放される進化、100,000Pで解放されるさらに上位の進化)

**ルート間の見た目とステータスの関係**:
知力ルート/筋力ルート、および天候・アイテム・フレンドの各特別ルートによる進化先の違いは、**見た目が異なるだけ**とし、進化後のステータスや性能そのものに差はつけない(図鑑コレクションの充実を目的とした要素と位置づける)。ただし、各ルートへの到達条件自体はステータス(知力系・筋力系有効度など)に依存するため、結果的に「筋力特化でなければ到達できない進化先」が生まれることは許容する。

**特別ルートの将来的な拡張**:
天候・アイテム・フレンドの3系統に加えて、育成ゲームとしての奥深さを高めるため、今後も特別ルートの種類を追加していく方針とする。例:図鑑(10.5節)を完全にコンプリートすると出現する「No.0」の特別な進化キャラクターなど。具体的な追加内容は今後の運用の中で検討する。

**進化条件(各段階共通の考え方)**:
1. その段階に一定時間以上滞在している(上表の期間)
2. 段階の必要時間を満たした時点(判定タイミング)で、満腹度・清潔度がそれぞれ一定値(例:60)以上である(スナップショット方式)。ただし卵はステータスを持たず、時間だけで孵化する(幼年期に入る時点で初期値を付与する。初期値は満腹度・清潔度100、機嫌50の暫定値)
3. (成熟期への進化のみ)有効度の閾値・優位差、または特別ルート条件を満たしている

**条件2の判定方法(確定):スナップショット方式**
- 過去の推移や平均は見ず、段階の必要時間を満たした「その時点」の満腹度・清潔度が基準値以上かどうかだけを判定する
- 条件を満たしていなければ進化は「保留」され、その後は判定を再実行するたびに(例えば満腹度・清潔度が変化するたびに)チェックし、基準を満たした時点で進化する
- 理由:本ゲーム全体の設計方針(条件未達は保留のみでペナルティなし、死亡条件も緩め、ルート差は見た目のみ)と一貫性があり、実装もシンプルになるため

**判定のタイミング(確定)**:進化の判定は、アプリを開いた時点、またはお世話をした時点で行う。放置中に段階の必要時間が満ちていても、時刻を遡って進化させることはせず、開いた(お世話した)時点の満腹度・清潔度で判定する。1回の判定で進むのは1段階までとし、新しい段階の時間は進化した時点から数える。

放置により条件2を満たせない場合は、通常は進化が「保留」されるのみで、ステータスの巻き戻しは行わない。ただし4.4節の条件を満たした場合に限り「死亡」が発生する。

### 4.4 死亡(バッドエンド)条件
- **発生条件**:満腹度が0の状態が24時間継続、かつそのとき清潔度が20%以下である場合
- 通常のお世話不足では発生しない、長期間の完全放置に対するペナルティとして位置づける
- **目安**:満タンの状態から一切お世話をしない場合、満腹度は約17時間で0になり、そこから24時間後(放置開始から約41時間後)に死亡する(清潔度もこの時点で0)。0の継続時間は、経過時間の上限(4.1節)に関わらず実際の時刻で数える。死亡は次にアプリを開いた時点で判定する
- **死亡後の処理**:「実は卵を1つ残していた」という設定にし、その卵から再スタートする。進化段階・有効度などの育成データはリセットされる(引き継ぎ要素の有無は12節で別途検討)

### 4.5 寿命による世代交代
- 放置による死亡(4.4節)とは別に、寿命を迎えた場合の「世代交代」を設ける
- **寿命**:成熟期到達から2週間(4.3節の元々の成熟期の期間と同じ長さ)
- **延命アイテム「長寿の秘薬」**:探索拠点での探索によって入手できるアイテム(ミニゲームクリア報酬のアイテムとは別系統の入手経路)。1個使用するごとに寿命が1週間延長される
- 寿命による死亡の場合に限り、ステータスボーナス付きの卵を残す
  - 先代の知力系有効度・筋力系有効度それぞれの5%をボーナスとして次の卵に引き継ぐ
  - 放置による死亡(4.4節)の場合はボーナスなしの卵になる(引き継ぎ要素なし)
- 「何代目」かを世代カウンターとして記録し、画面上に表示する(表示箇所は9節で検討)
- **実装上の取り決め**:
  - 寿命の判定は、放置による死亡(4.4節)と同様に次にアプリを開いた時点で行う。両方の条件が成立している場合は、先に成立した時刻のほうを採用する(寿命が先ならボーナスあり、放置死亡が先ならなし)
  - 引き継ぎボーナスは、卵が保持し、孵化して幼年期に入る時点で有効度として付与する(卵自体はステータスを持たない)
  - 「長寿の秘薬」は成熟期のみ有効で、複数個使うと1個ごとに1週間ずつ積み上がる。寿命を迎えた後には使えない

### 4.6 見た目との連動
- 満腹度が30以下、または機嫌が30以下になると、通常表示フレームが sad 系に自動的に切り替わる
- 清潔度が0になると、キャラクターに煤(すす)とアホ毛を数本追加した専用フレームを表示する(10.2.2節)
- 進化段階が変わるとキャラクター全体の見た目(フレーム一式)を差し替える

### 4.7 ステータス表示方針(UI)
- ステータスは大々的に見せない方針とする。内部値は100段階で管理しつつ、UI表示はアイコン+10段階のドット表記に丸めて簡易表示する
- 表示場所はメイン画面下部(詳細はセクション8.2)

### 4.8 天候システムと育成への影響
- 天候の種類:晴れ・曇り・雨・雪・雷雨の5種類とする
- 桜吹雪などの季節演出は天候種別とは別枠の「季節演出レイヤー」として扱い、天候(晴れ〜雷雨)と重ねて表示できるようにする(例:桜吹雪の期間中に「曇り+桜吹雪」も起こり得る)
- 桜吹雪の表示期間:4/1〜4/15(固定)
- 実際の天気と連動させる(詳細な仕組みはセクション9.3を参照)
- 天候ごとの累積ケア回数(例:雨の日にお世話した回数)を記録し、進化の特別ルート(4.3節)の条件として使用する。天候ルートはレアな進化として位置づけ、通常の知力/筋力ルートとは別枠で扱う

- **機嫌**:プレイ後の機嫌は +10 の一定値(5.4節「スコアに関わらず一定値」を採用。4.1節の「成績に応じて +5〜15」とは食い違うため要確認)

## 6. ミニゲーム2:カード×NPC戦 詳細設計

### 6.1 概要
オリジナルのカード体系を用いた、目標数字への近さと運を競うNPC対戦ゲーム(ブラックジャックの骨格を採用、名称・意匠は完全オリジナル)。

### 6.2 ルール
- オリジナルカード:数字1〜10相当を独自の意匠(属性アイコン等)で表現。スート概念は簡略化するか独自属性に置き換える(具体的な意匠は6.2.1節)
- **対戦形式(コイン賭け)**:双方5枚のコインを持ってマッチを開始する
- **各ラウンド**:ラウンド開始時に賭けるコイン枚数を選択する(**1〜3枚まで**。1ゲーム目で全額を賭けて即決着することを防ぐための上限)。目標値(例:20)を超えないよう、カードを引く/止めるを選択し、手札合計が目標値に最も近い側がそのラウンドの勝者となる。勝者は賭けた枚数を敗者から獲得する(超過した場合は即敗北)
- **マッチ終了条件**:5ラウンドを消化する、またはどちらかのコインが0枚になった時点でマッチ終了(圧勝の場合は5ラウンド未満で終わる)
- **マッチの勝敗**:終了時点でコインを多く持っている側の勝ち
- **同数(引き分け)の場合**:「無効試合」として扱う。勝敗・連勝数には影響しないが、知力系有効度をごく少量(通常勝利より大幅に少ない量)加算する
- 1日のプレイ回数上限:3回(1回=1マッチ。リワード広告視聴で追加可能、詳細は2.2節)

#### 6.2.1 カードの意匠(確定)
- スートの代わりに、天候システム(4.8節)と同じ5属性(晴れ・曇り・雨・雪・雷雨)を使用する
- 各属性で1〜10の数字カードを用意する(5属性×10数字。必要に応じて実装時に枚数を調整)
- 天候アイコンをそのままカードのシンボルとして流用することで、新たな意匠を一から起こす手間を省きつつ、ゲーム全体の世界観に一貫性を持たせる

### 6.3 NPC設計
- 他2本のミニゲームと共通の難易度構成に合わせ、初級/中級/上級の3段階のNPCとする(勝ち上がり式:初級に勝利すると中級が解放、中級に勝利すると上級が解放)
- NPCの意思決定は固定ロジック(閾値に応じてカードを引く/止める)、難易度が上がるほど閾値が最適化される
- クリア判定:該当難易度のNPCに勝利することを「クリア」とする
- 他2本が「目標スコア」で難易度を表すのに対し、本ゲームは対戦形式のため「NPCが手を止める基準値」を難易度パラメータとする(下表、叩き台。目標値20を想定)

| 難易度 | NPCが引くのを止める手札合計の目安 |
|---|---|
| 初級 | 15以上で止める(やや保守的で超過しやすい) |
| 中級 | 17以上で止める |
| 上級 | 19以上で止める(ほぼ最適な立ち回り) |

**NPCの見た目(確定)**
黒い靄のような人影のシルエットを基本デザインとし、難易度が上がるごとに禍々しさが増す段階的な見た目にする。

| 難易度 | 見た目 |
|---|---|
| 初級 | 黒い靄のような人影のシルエット+赤い目 |
| 中級 | 初級の見た目に加えて、笑っているような赤い口が追加される |
| 上級 | 中級の見た目に加えて、悪魔のような角のシルエットが生える |

見た目の変化そのもので「格上の相手」であることが直感的に伝わるデザインとする。

### 6.4 モンスターカード(育成要素との接続)
- プレイヤーが育てたモンスターの進化段階に応じた「特殊効果カード」を1戦につき1枚まで持ち込み可能
  - 例(幼年期):手札を1枚多く見られる
  - 例(成長期):1回だけ引き直しができる
  - 例(成熟期・ルート別):知力ルート→合計値のブレを軽減、筋力ルート→超過時に1回だけ耐える

### 6.5 育成への反映
- マッチ勝利(6.2節):連勝数+1、知力系有効度+
- マッチ敗北:連勝数リセット、有効度への影響なし(ペナルティを与えすぎず、気軽に再挑戦できる設計)
- 無効試合(コイン同数):連勝数・勝敗には影響しないが、知力系有効度をごく少量加算する
- 1日あたりの有効度獲得上限あり
- クリア報酬(探索ポイント・アイテム)は8.5節の共通仕様に従う

### 6.5.1 実装上の取り決め(暫定値。プレイテストで調整)
設計書に記載がなかった部分は、以下の暫定の扱いで実装している(`CardConfig` / `CardRewardConfig` で変更できる)。
- **配札**:各ラウンドで全 50 枚を切り直し、双方に 2 枚ずつ配る。NPC の 2 枚目は伏せ札(ラウンド終了まで見えない)。プレイヤーが先に「引く/止める」を行い、止めたあと NPC が閾値まで引く
- **賭け**:プレイヤーが選んだ枚数を双方が賭ける。賭けられるのは、3 枚・自分の残り・相手の残りのうち最小の枚数まで(負けた側が払えなくならないように)
- **ラウンドの決着**:プレイヤーが超過したら NPC は引かずに即敗北。NPC が超過したらプレイヤーの勝ち。それ以外は合計が大きい(目標値に近い)側が勝ち。同点のラウンドはコインが動かない
- **マッチ終了**:5 ラウンドを終える、またはどちらかのコインが 0 枚になった時点。コインが多い側の勝ち、同数は無効試合
- **NPC の強さ**:手札の合計が閾値(初級 15、中級 17、上級 19)以上になるまで引く
- **モンスターカード**(1 戦に 1 回まで):幼年期は「先読み」(相手の伏せ札を見る)、成長期Ⅰ・Ⅱは「引き直し」(直前のカードを引き直す)、成熟期の知力ルートは「見極め」(次に引くとき 2 枚引いて目標値に近いほうを選ぶ)、筋力ルートは「耐える」(超過を 1 回だけ免れ、超えたカードを捨てて止める。自動で発動)。ルートは、進化時の状態を記録していないため、現在の有効度の優劣で判定する(同数は知力ルート)。効果の内容は、実際のプレイ感を見て変更する予定
- **育成への反映**:勝利で知力系有効度を加算(初級 +8、中級 +12、上級 +16。加算量はプレイテストの様子を見て調整する)、無効試合は +1、敗北は加算なし。筋力系は加算しない。機嫌は勝敗に関わらず +10。有効度は 1 日の上限(2.2節の取り決め)の対象
- **勝ち上がり**:初級に勝つと中級、中級に勝つと上級が解放される。連勝数は勝利で +1、敗北で 0、無効試合は変えない
- **NPC の見た目**:本番のドット絵ができるまで、黒い靄+赤い目(中級で赤い口、上級で角)を図形で仮描画している

### 6.6 ランキング
- 連勝数によるフレンド限定リーダーボード
- **連勝数(=通算の不敗記録)と通算成績(確定)**:連勝数は、勝利で +1、敗北で 0。無効試合(引き分け)は数えず、途切れさせもしない(引き分けを挟んでも、負けない限り次の勝利で続けて数える)。1 回のマッチに限らず通算で数えるので、これがそのまま通算の不敗記録になる。通算成績(勝・敗・無効試合)も記録する。ランキングで共有する値は、連勝数の最高記録(9.1節)
- 連勝数はサーバー側で軽く整合性チェック(あり得ない連勝数を弾く)

## 7. ミニゲーム3:壁破りゲーム 詳細設計

### 7.1 概要
育てたモンスター本人が前進しながら、指令に合う色の壁を選んで破壊していくストループ効果(色と文字の不一致を利用した判断ゲーム)ベースのアクション。筋力系有効度の主な獲得手段と位置づける。

### 7.2 ルール
- 画面中央に指令(色名の単語を、その意味とは異なるインク色で表示した文章)が出る
- 指令の単語表記:英語・漢字・ひらがなのいずれかでランダムに表示する(例:「RED」「赤」「あか」)。表記の種類も判断材料の一つになる
- プレイ開始時に「文字色ルール(インクの色に合う壁を選ぶ)」か「単語ルール(書かれている色名の意味に合う壁を選ぶ)」のどちらかに決定され、そのプレイ中は固定
- 正面に複数の色付きの壁が並び、指令に合う壁へ進む
- 正解:モンスターが壁を破壊して前進する演出
- 不正解:モンスターが壁に衝突する演出+残り時間を3秒減少
- 制限時間:60秒のタイムアタック(他の2本と統一)
- 1日のプレイ回数上限:3回(リワード広告視聴で追加可能、詳細は2.2節)

**難易度と壁の構成**

| 難易度 | 壁の枚数 | 使用する色 |
|---|---|---|
| 初級 | 2枚 | 赤・黄・青・緑・黒(基本5色) |
| 中級 | 3枚 | 基本5色+紫(6色) |
| 上級 | 4枚 | 基本5色+紫・オレンジ(7色) |

紫・オレンジは中級・上級で追加される色とし、初級では登場しない。

クリア判定:選択した難易度の目標スコア(壁突破数)に到達することを「クリア」とする(下表、叩き台)。

| 難易度 | 目標スコア(壁突破数) |
|---|---|
| 初級 | 15 |
| 中級 | 25 |
| 上級 | 35 |

### 7.3 ミス無効システム(筋力連動)
- 育てたモンスターの筋力系有効度に応じて、不正解時のペナルティ(時間減少)を無効化できる「ミス無効」回数を持つ
- 筋力値100/200/300ごとに1回ずつ解放され、進化段階ごとに上限回数を設ける

| 進化段階 | ミス無効の上限回数 |
|---|---|
| 成長期Ⅰ | 最大1回 |
| 成長期Ⅱ | 最大2回 |
| 成熟期 | 最大3回 |

- 付与回数の計算式:`付与回数 = min(その段階の上限, floor(筋力値 / 100))`
  - 例:成熟期で筋力210の場合、floor(210/100)=2 → ミス無効2回付与
- ミス無効を使用した場合、時間減少ペナルティは発生せず壁は破壊されるが、その回の連続正解ボーナス(コンボ)は無効になる

### 7.4 スコアリング
- 突破した壁の枚数がそのままスコアになる
- 連続正解(コンボ)にボーナス倍率を設定(ミス無効を使った回はコンボ対象外、7.3節参照)

### 7.5 育成への反映
- 最終スコアに応じて筋力系有効度を加算(1日あたりの獲得上限あり)
- プレイ後の機嫌+も別途付与
- クリア報酬(探索ポイント・アイテム)は8.5節の共通仕様に従う

### 7.5.1 実装上の取り決め(暫定値。プレイテストで調整)
設計書に記載がなかった部分は、以下の暫定の扱いで実装している(`WallBreakConfig` / `WallBreakRewardConfig` で変更できる)。
- **指令と壁**:単語の意味とインク色は必ず異なる。壁には、正解の色に加えて「もう一方のルールでの正解の色(ひっかけ)」を必ず含め、残りは使える色からランダムに選ぶ。壁の並び順と単語の表記(英語・漢字・ひらがな)もランダム
- **不正解のあと**:壁に衝突して残り時間が 3 秒減り、そのまま新しい指令に進む(同じ指令のやり直しはしない)
- **ミス無効**:時間は減らず壁は破壊される(突破数 +1、基本の 1 点)。コンボは通常のミスと同じく 0 に戻り、その回は倍率の対象外
- **コンボ**:連続正解 1 段ごとに、1 枚あたりの得点に ×0.1 が加わる(2 連続目 ×1.1 … 上限 ×2.0)。スコアは倍率を含めた合計の切り捨て
- **クリア判定**:目標は「突破数」(ミス無効で破壊した壁を含む)で判定する。コンボで増えたスコアではなく突破数で判定し、達成後も制限時間まで続けられる
- **育成への反映**:筋力系有効度を `floor(スコア ÷ 2)` 加算(暫定。様子を見て調整)、機嫌は +10 の一定値。知力系は加算しない。有効度は 1 日の上限(2.2節の取り決め)の対象
- **ミス無効の回数**:筋力系有効度と進化段階から求める(7.3節)。卵・幼年期は 0 回。装備アイテム(筋力の装備など)は、筋力系有効度の増加量に上乗せされるので、その分ミス無効の回数にも間接的に効く(8.4.1節)
- **見た目**:モンスターは前進中に walk、正解で attack、ミスで damage のフレームを表示する。
  - 壁の破壊演出:正解(ミス無効を含む)のとき、壁が砕けて破片がはじけ飛ぶ(約 0.7 秒。破片は中心から四方に飛び、重力で落ちながら小さく・薄くなって消える)
  - 壁の絵:ドット絵を `assets/wallbreak/walls/<色名の小文字>.png`(`red.png` `yellow.png` `blue.png` `green.png` `black.png` `purple.png` `orange.png`)に置くと、その色の壁として使われる(整数倍・補間なし)。置かれていない色は、色付きの四角で表示する

### 7.6 ランキング
- ローカルのハイスコア記録
- フレンド限定リーダーボード(他2本のミニゲームと同様の構成)

## 8. 探索機能 詳細設計

### 8.1 概要
探索拠点で行える、探索ポイントを消費してアイテムを入手するコンテンツ。ミニゲームと並ぶ、拠点を活かした遊びの1つと位置づける。

- 探索箇所は初期リリース時点で3種類用意する:**洞窟・海岸・山**
- ミニゲームと同様、今後も探索箇所を追加していく想定とする(ロードマップPhase 9の継続運用に対応)
- 初期の3探索箇所+3本のミニゲームで、装備アイテム6種(8.4節)それぞれの入手源として1つずつ固定対応させる(対応関係は8.4節を参照)

### 8.2 探索ポイントと所要時間
- ログイン時に100ポイントとごはん3個を付与(1日1回。アプリを開いたとき、および日付が変わったときに付与する。確定。満腹度は1個で+25、1日で約144減るため、ごはんはほかに探索・ミニゲームでも手に入れる想定)
- はじめて始めたときに、ごはん10個をプレゼントする(一度だけ。確定)
- 探索1回につき100ポイント消費(ログイン時の付与分で1日1回無料で探索できる計算になる)
- ポイントの上限はなし(繰り越し可能。使わなければ翌日以降も貯まっていく)
- ミニゲームのクリア報酬としても探索ポイントを獲得できる(8.5節)
- **所要時間**:探索1回につき30分
- **連続探索(10連)**:探索ポイント1000を消費し、10回分をまとめて実行できる。所要時間は本来5時間(30分×10回)だが、まとめて行うことによるボーナスで4時間に短縮される

### 8.3 報酬内容とレアリティ
- 探索1回につき、アイテムを3個入手する(3個それぞれ独立してレアリティを抽選する)
- 連続探索(10連)の場合は、10回分まとめて計30個のアイテムを入手する
- レアリティと排出確率は以下のとおり

| レアリティ | 排出確率 | 内容 |
|---|---|---|
| ノーマル | 91.5% | ごはん |
| レア | 5% | ミニゲーム券 |
| かなりレア | 3% | 装備アイテム |
| 超レア | 0.5% | 長寿の秘薬(4.5節) |

「かなりレア」で装備アイテムが出た場合、その探索箇所(または該当ミニゲームの上級初回クリア)ごとに固定で対応する1種類が入手できる(8.4節)。

### 8.4 アイテム効果
- **ミニゲーム券**:対象ミニゲーム1回分のプレイ回数を追加できる券。1日のプレイ回数上限(2.2節、通常3回)に達した際、リワード広告を視聴するかミニゲーム券を使用するかをプレイヤーが選択できる
- **装備アイテム**:主に以下の効果を持つ
  - 進化の特別ルート(4.3節アイテムルート)の条件として機能する
  - ステータス(知力系・筋力系有効度等)のアップ、または満腹度・清潔度の減少速度を下げる(お世話の手間を軽減する)効果を持つ

**装備アイテムのカタログ(初期案・6種)**

| 種類 | 効果 |
|---|---|
| 筋力の装備 | 筋力系有効度 +5% |
| 知力の装備 | 知力系有効度 +5% |
| 満腹の装備 | 満腹度の減少速度 -5% |
| 清潔の装備 | 清潔度の減少速度 -5% |
| バランスの装備(有効度) | 筋力系有効度 +2.5%、知力系有効度 +2.5% |
| バランスの装備(お世話) | 満腹度の減少速度 -2.5%、清潔度の減少速度 -2.5% |

単体特化型(±5%)とバランス型(±2.5%×2)を対にする構成とする。

**入手源との対応関係(確定)**

| 入手源 | 装備アイテム |
|---|---|
| ミニゲーム1(落ち物パズル) | バランスの装備(有効度) |
| ミニゲーム2(カード×NPC戦) | 知力の装備 |
| ミニゲーム3(壁破りゲーム) | 筋力の装備 |
| 探索(洞窟) | バランスの装備(お世話) |
| 探索(海岸) | 清潔の装備 |
| 探索(山) | 満腹の装備 |

### 8.4.1 装備・長寿の秘薬の実装上の取り決め(暫定値。プレイテストで調整)
設計書に記載がなかった部分は、以下の暫定の扱いで実装している(`core/minigame/Equipment.kt`)。
- **装着の仕組み**:装備は消費しない(使っても減らない)。所持している装備を、持ち物画面(10.2.5節)で装着・取り外しする。装着枠は「有効度の枠」(筋力の装備・知力の装備・バランスの装備(有効度))と「お世話の枠」(満腹の装備・清潔の装備・バランスの装備(お世話))の 2 つで、同じ枠には 1 つだけ装着できる(別の枠とは同時に装着できる)。単体特化型とバランス型を対にする構成(8.4節)に合わせ、同じ枠の中でどちらかを選ぶ形にした
- **有効度の装備の効果**:ミニゲームで得た知力系・筋力系有効度の**増加量**に、+5%(バランス型は両方 +2.5%)を上乗せする。1 日の獲得上限(2.2節)を適用したあとの量に上乗せするので、上限の消費は上乗せ前の量で数える。機嫌は対象外。すでに貯まっている有効度そのものは変えない(先代からの引き継ぎ・進化の判定・ミス無効の回数の判定は素の値)
- **お世話の装備の効果**:満腹度・清潔度の自然減少の速度を -5%(バランス型は両方 -2.5%)する。最大の軽減(5%)でも、満タンから 24 時間の上限より前に 0 へ届く(4.1節・todo の方針を保つ)。装着・取り外しの直前までの減少は、それまでの装備で反映してから切り替える(さかのぼって効果が変わらない)
- **進化のアイテムルート**(4.3節)の条件としての使い方は、進化因子の具体的な条件(10.5節)が決まってから実装する。**未実装**
- **長寿の秘薬**:持ち物画面から使う。成熟期のみ有効で、1 個ごとに寿命が 1 週間延びる(複数個は積み上がる)。経過時間を反映した結果、すでに寿命・死亡で卵になっていた場合は使えず、秘薬は減らない

### 8.5 ミニゲームクリア報酬(共通仕様)
ミニゲーム1〜3はいずれも初級・中級・上級の3段階の難易度を持ち、クリア時の報酬は共通仕様として以下のとおりとする。

| 難易度 | 探索ポイント | アイテム |
|---|---|---|
| 初級 | 50 | ノーマル×1 |
| 中級 | 75 | ノーマル×1、レア×1 |
| 上級 | 100 | ノーマル×1、レア×2 |

- 上級クリアのみ、**初回クリア時に限り**、かなりレア(装備アイテム)を1つ追加で入手できる
- 本表は5.4節・6.5節・7.5節の「クリア報酬」の共通仕様として参照する

### 8.6 探索の画面の流れと実装上の取り決め
**画面の流れ(確定)**
1. ワールドマップ(10.4節)で探索拠点(洞窟・海岸・山)を選ぶ
2. 拠点の画面に移り、導入の文章と選択肢が表示される。例(洞窟):「暗くて巨大な洞窟があります。探索をしますか?」→ `探索する` / `この場を離れる`
3. `この場を離れる` を選ぶと、ワールドマップに戻る
4. `探索する` を選ぶと、`少し探索(1回)` / `じっくり探索(10回)` を選べる(消費する探索ポイントと所要時間も表示する)
5. 選んだあと、キャラクターが背景のほうへ小さくなっていく演出(探索に出かけるアニメーション)を再生し、探索が始まる
6. 探索中は `探索中(残り〜)` と表示する(例: 探索中(残り 3時間30分))。ワールドマップの拠点ボタンにも同じ表記を出す
7. 探索が終わると `探索が終わりました!` と表示し、`成果を受け取る` でアイテムを持ち物へ受け取る

**暫定の取り決め(プレイの様子を見て調整)**
- **同時に探索できる数(確定)**:ふだんは 1 か所。フレンドがいる場合は、2 か所追加で合計 3 か所まで同時に探索できる。同じ拠点は重ねて探索できない。2 か所目以降で `探索する` を選んだときは、「フレンドが協力しに来てくれました!」と表示し、そのあと 1 か所目と同じように回数(少し探索/じっくり探索)を選ぶ。フレンド機能(Phase 7)ができるまでは、マップ画面の動作確認用のスイッチで代用する
- 報酬(アイテム 3 個 × 回数)は、探索を始めた時点で抽選して保存する。受け取りは、終わってから
- 卵の間は探索に行けない(ミニゲームと同じ扱い)
- **探索中のキャラクター(確定)**:メイン画面を表示すると、数秒(約 3 秒)遅れて、画面の外から歩いて戻ってくる。ウィジェットではキャラクターは消えず、探索中は `探索中(残り〜)`、完了したら `探索完了!` と表示する(複数の拠点を探索中は、最短の残り時間と拠点数を表示する)。探索中も育成(お世話・ミニゲーム)は行える
- **完了の通知(確定)**:探索が終わる時刻に、端末へ通知を出す(拠点ごと)。ウィジェットも完了の表示に切り替わる。Android 13 以降は、通知の許可を実行時に求める。許可されていなければ通知は出ない
- ログインボーナス(1 日 1 回、探索ポイント +100 とごはん +3)は、アプリを開いたときに付与する(日付が変わったときにも付与する)
- 拠点の導入文は、洞窟以外(海岸・山)は仮の文章。背景は本番の画像ができるまで色のグラデーションで仮表示する

### 9.1 ランキングの共有方針(方向性。Phase 6・7 で実装)
- **共有する値(確定)**:各ミニゲームの「トップスコア」は、これまでの自己ベスト。対象は、落ち物パズル・壁破りゲームのスコアと、カード×NPC戦の連勝数(最高記録)。カード×NPC戦の連勝数は、通算の不敗記録(引き分けは数えず、負けるまで続く)でもある(6.6節)
- **共有のタイミング(推奨案。確認待ち)**:時刻へのこだわりはない。深夜 0 時に固定せず、**自己ベストが更新されたときだけ**端末に「未送信」を記録し、アプリを開いたときと、バックグラウンドの定期処理(1 日数回。例: 6 時間ごと)にまとめて送る。更新がなければ何も送らない。理由:書き込みが少なくて Firestore の無料枠に十分収まる/0 時に端末が動いている保証がない/更新が(次の定期処理までに)早く反映される
- **表示**:リアルタイムには更新せず、サーバーにある共有済みの値を、ランキングを開いたときに取得して表示する(2.1節の「都度フェッチ+ローカル演出」の方針と一致)
- あり得ない値の簡易チェックは、Cloud Functions 側で行う(5.5節・6.6節)

**フレンドシップポイントの獲得手段(確定)**

| アクション | 獲得ポイント | 頻度制限 |
|---|---|---|
| いいね(送信側) | 100P | **1日1回のみ**(何人のフレンドに送っても、送信側が獲得できるのは1日100Pが上限) |
| いいね(受信側) | 100P | 上限なし(フレンドから「いいね」をもらうたびに加算。フレンドごとに1日1回まで送られてくる) |

いいねは、送信側と受信側で獲得ルールが異なる非対称仕様とする(送信側の稼ぎすぎを防ぎつつ、多くのフレンドから慕われるほど受信側の獲得は伸びる設計)。お世話代行・プレゼント送付・応援スタンプは、双方向アクション系の機能として今回は見送り、初回リリースの双方向交流は「いいね」と「ランキングによる緩い競争」に絞る。

### 9.2 フレンド画面の骨組み(実装上の取り決め)
サーバー(Firebase。Phase 6・7)ができるまでは、画面の構成と、端末内でできる部分だけを実装している。
- **画面の構成**:フレンドシップポイント、フレンド一覧(最終ログイン・「いいね」)、フレンドの追加、ランキング(自分の自己ベスト)の順
- **フレンドシップポイント**:「いいね」の送信は 1 日に 1 回 100P(何人に送っても、最初の 1 回だけ)、同じフレンドには 1 日 1 回まで。もらった「いいね」は 1 回ごとに 100P(上限なし)。端末内に保存する
- **フレンド一覧**:実際のフレンドは、サーバー機能ができるまで表示されない(「準備中」)。動作確認用に、開発用画面のスイッチで仮のフレンド 2 人を表示できる(探索の同時実行・協力の表示と共通)
- **ランキング**:フレンドとの比較は準備中。自分の自己ベスト(落ち物パズル・壁破りゲームの難易度別スコア、カード×NPC戦の連勝の最高)を表示する。9.1節の方針で共有する値と同じ
- ログイン状況・ステータスの表示 ON/OFF は、設定画面(10.6節)で切り替える

詳細な画面仕様・データ構造はPhase 7実装時に本書へ追記する。

#### 10.2.1 餌やり(ドラッグ&ドロップ)の実装方式
- **本体アプリ限定の操作とする**。ウィジェット(RemoteViews/Glance)はジェスチャー検知に対応できないため、ウィジェット側は引き続き単純タップの「餌やり」ボタンを用意する(Phase 3節の方針を踏襲。ウィジェットとアプリでインタラクションの複雑さが異なる点は仕様として明記しておく)。ウィジェットの餌やりも、アプリと同じくごはんを1個消費する(確定)。ボタンにはごはんの残り数を表示し、ごはんが0個・卵の間は押せない
- Compose実装方針(叩き台):
  1. リュックパネル内の餌アイテムに `Modifier.pointerInput` + `detectDragGestures` を設定し、ドラッグ開始・移動・終了を検知する
  2. ドラッグ中は指の移動量を状態(`Offset`)として保持し、餌アイテムのアイコンを画面上に指の位置に追従させて表示する(通常のレイアウトから浮かせて描画する)
  3. ドラッグ終了時、指を離した座標がキャラクター表示領域の境界(`onGloballyPositioned` で取得)と重なっているかを判定する
  4. **重なっていた場合(給餌成立)**:満腹度を加算(4.1節)、アイテムを1つ消費、キャラクターの表情を食事アニメーション(3章の差分画像切り替え方式、eat系フレーム)に切り替える。あわせてハートマークを表示し、喜ぶモーション(happy系フレーム)を再生する
  5. **重なっていなかった場合(キャンセル)**:アイテムをリュックの元の位置までアニメーションで戻す

#### 10.2.2 掃除(タップ→スワイプ)の実装方式
- **動作フロー**:
  1. リュックパネルのそうじ道具アイコンをタップすると「掃除モード」に入る(道具を持った状態になる)
  2. 掃除モード中、拠点の背景上に表示されている汚れ(デカール)をスワイプでなでると、なでた回数が加算される
  3. 1箇所の汚れにつき**5回なでる**と、その汚れが消える演出とともに清潔度が**+20**される
  4. すべての汚れを落とすと自動的に掃除モードが終了し、完了演出(例:「きれいになった!」)を表示する
  5. 掃除モード中に汚れ以外の場所をタップする、またはそうじ道具アイコンを再度タップすることで、いつでも掃除モードを終了できる(残っている汚れはそのまま残り、なでた回数は持ち越さずリセットする。確定)
- **本体アプリ限定の操作とする**(理由は10.2.1節と同様、ウィジェットはジェスチャー非対応のため単純タップの「掃除」ボタンを維持)

**汚れの表示個数と清潔度の対応(確定)**

| 清潔度 | 表示される汚れの数 |
|---|---|
| 80未満 | 1箇所 |
| 60未満 | 2箇所 |
| 40未満 | 3箇所 |
| 20未満 | 4箇所 |
| 0 | 5箇所 |

汚れ1箇所を消す(5回なでる)ごとに清潔度+20となるため、5箇所すべて消すと清潔度は満了する計算になる。この整合を保つため、汚れは「清潔度が上表の数を下回ったとき」に現れ、掃除で消したとき以外には減らない(清潔度0の5箇所から1箇所ずつ消すと、残りが 4→3→2→1→0 と減り、5箇所目で100になる)。掃除以外の方法で清潔度が上がった場合は、満タンまでに必要な数(`ceil((100−清潔度)÷20)`)を超えた汚れだけが消える

**見た目の表現**
- 通常の汚れ:拠点の背景上に紙屑・泥などのデカールとして表示する(位置は候補地点からランダムまたは固定パターンで抽選)
- 清潔度0の特別演出:上記の背景の汚れ5箇所に加えて、キャラクター本体に煤(すす)とアホ毛を数本追加した専用フレームを表示する(3章の差分画像切り替え方式に「煤+アホ毛」状態のフレームを追加する。4.6節の見た目連動ルールにも追記する)

- Compose実装方針(叩き台):
  1. 汚れの位置を拠点の背景上の複数点(`Offset`のリスト)として保持する。清潔度の閾値(上表)に応じて表示数を増減させる
  2. 各汚れに「なでた回数」カウンターを持たせる
  3. 掃除モード中は `Modifier.pointerInput` + `detectDragGestures` でスワイプ(なでる動作)を検知する
  4. スワイプが汚れの位置から一定半径以内を通過するたびに、その汚れのカウンターを+1する
  5. カウンターが5に達したら、その汚れを除去し(消去アニメーション)、清潔度を+20する
  6. 汚れをすべて除去したら掃除モードを自動終了する

#### 10.2.3 キャラクターからのプレゼント
- **概要**:ごく稀に、キャラクターがプレイヤーにアイテムをプレゼントする演出を用意する
- **表示**:プレゼントが発生すると、キャラクター付近に「・・・」という文字を表示したコメントの吹き出しアイコンが表示される(ボタンではなく、吹き出し自体がタップ対象)
- **操作**:吹き出しアイコンをタップすると、モーダルで「『(キャラクター名)』がプレゼントを渡したいようです。」というメッセージとアイテムアイコンを表示する
- **複数プレゼントがある場合**:一度に全ては表示せず、1つのプレゼントを受け取り済み(モーダルを解消)にした後、再び吹き出しアイコンが表示されて次のプレゼントに進む
- **発生条件**:通常プレイ中にランダムで発生するデフォルト機能としては実装しない。桜吹雪(4.3節)のような期間限定イベント時にのみ、運営側の設定(Firebase Remote Config等)で発生させる、イベント専用のアイテム配布手段として位置づける

#### 10.2.4 お世話操作の実装上の取り決め(暫定を含む)
メイン画面(本体アプリ)のお世話操作を、次のとおり実装している(ウィジェットは従来どおり単純タップのボタン)。
- **なでる**:キャラクター本体をタップする(機嫌 +10、happy の演出、ハートを表示)。掃除モード中・卵の間は反応しない
- **餌やり**:リュックを開き、ごはん(所持数を表示)をキャラクターへドラッグ&ドロップする。離した位置がキャラクターに重なれば給餌成立で、ごはんを 1 つ消費し、満腹度 +25・機嫌 +5、eat → happy の演出。外れたときは、ごはんが元の位置へ戻る。ごはんが 0 個の間は与えられない。ごはんは、ログインボーナス(1 日 3 個。8.2節)・はじめてのプレゼント(10 個)・ミニゲームのクリア報酬・探索で手に入る
- **掃除**:リュックの「そうじ道具」で掃除モードに入る。汚れは背景の上の 5 つの候補地点に、清潔度に応じた数だけ表示する(10.2.2節の表)。指が汚れのそばを通過するたびになでた回数が +1(同じ汚れの上で動き続けても 1 回)され、汚れが薄くなり、5 回で消えて清潔度 +20。すべて落とすと自動で掃除モードを終え、「きれいになった!」と表示する。汚れ以外の場所をタップしても終えられる。残った汚れは残り、なでた回数は掃除モードを終えるとリセットされる(持ち越さない。確定)
- **汚れの数と清潔度の整合**:汚れは表どおりの数を下回ったとき(清潔度 79.9 で 1 箇所目 … 0 で 5 箇所)に現れ、掃除で消したとき以外には減らない。1 箇所 +20 で、清潔度 0 の 5 箇所をすべて消すとちょうど 100 になる。掃除以外で清潔度が上がったときは、満タンまでに必要な数を超えた汚れだけが消える
- **確認用ボタン**:育成画面の「デモ」の餌・掃除・なでるボタンは、動作確認用として残している(餌のデモボタンはごはんを消費しない)

#### 10.2.5 持ち物画面(暫定)
メイン画面のリュック(餌・そうじ道具。10.2節)とは別に、持ち物をまとめて見て使う画面をヘッダーのメニュー(☰)から開く。
- 持ち物の一覧:探索ポイント・ごはん・ミニゲーム券の所持数
- 長寿の秘薬:所持数と寿命までの残り日数の表示、`使う` ボタン(成熟期のみ。8.4.1節)
- 装備:6 種の所持数と効果の表示、`装着` / `外す`(8.4.1節)。未所持の装備は装着できない
- 戻る操作でメイン画面へ戻る

### 10.3 背景・天候システム
- 背景は「拠点(ロケーション)」ごとに切り替わる(例:森、廃屋)。拠点は将来的に追加できる構成とする
- 天候は背景の上に重ねるレイヤーとして表現する(雨・曇り・雪・雷雨のパーティクル/演出)。季節演出(桜吹雪など)はさらに別レイヤーとして重ね、天候と季節演出は独立して組み合わせられる。拠点の背景・天候・季節演出はすべて独立したレイヤーとする
- 天候は実際の天気と連動させる:
  - 端末の位置情報+OpenWeatherMap(2節参照)から現在の天気を取得する
  - APIキー保護のため、端末から直接APIを叩かずCloud Functions経由で取得する
  - 取得頻度は1日数回程度で十分(既存の非同期設計方針に合わせる。WorkManagerによる定期実行を想定)
  - **位置情報許可の導線**:初回にメイン画面表示時(または天候アイコン初表示のタイミング)で許可ダイアログを表示する。設定画面から後から許可し直せる導線を用意する
  - **位置情報が許可されなかった場合**:実際の天気と連動させず、年間の天気出現比率に基づいた確率表示に切り替える(下表)。1日1回抽選し、その日は同じ天候を保持する(実際の天気と同じ更新頻度感に合わせる)
  - **オフライン・API取得失敗時のフォールバック**:直近に取得できた天候値をローカルに保持し、新規取得に失敗した場合は保持している前回値を使い続ける。初回起動で一度も取得できていない場合は、位置情報が許可されなかった場合と同じ確率表示にフォールバックする

**年間天気出現比率(位置情報が使えない場合のデフォルト値)**

| 天気 | 割合 |
|---|---|
| 晴れ | 40% |
| 曇り | 30% |
| 雨 | 22% |
| 雷雨 | 3% |
| 雪 | 5% |

日本の一般的な傾向を仮定した全国一律の目安値とする(地域別の出現比率は実装・運用コストを考慮し設けない)
- 天候は育成の記録要素としても使う。天候ごとの累積ケア回数を進化条件(4.3節)に反映する

### 10.4 ワールドマップ画面
- 拠点(自宅/ゲーム拠点/探索拠点など)をアイコンで配置した地図画面
- 探索拠点は初期3種類(洞窟・海岸・山)を個別のアイコンとして配置する(8.1節)。ミニゲーム同様、今後の追加に対応できる構成とする。メイン画面の背景拠点(森・廃屋など、10.3節)とは別の概念であり、名称も重複しないようにする
- 現在地には育成中のキャラクターの小さいアイコンを表示する
- 拠点間を結ぶ固定ルート(点線など)は表示しない。プレイヤーが自由に行き来している感覚を優先する
- 未解放の拠点はグレーアウト表示し、将来的な拠点追加に対応できる構成とする
- 拠点をタップすると、その拠点に対応する画面(ゲーム選択画面、探索画面など)へ遷移する
- 探索拠点では「長寿の秘薬」(4.5節)などのアイテムを入手できる(探索機能の詳細は8節を参照)
- 拠点をタップすると探索拠点の画面に移り、「探索をしますか?」の選択肢(`探索する` / `この場を離れる`)が表示される。`この場を離れる` でワールドマップに戻る(画面の流れは8.6節)

#### 10.4.1 画面遷移とワールドマップの実装上の取り決め(暫定を含む)
- **画面遷移**:メイン画面(育成画面)を起点に、ヘッダーの地図アイコンからワールドマップへ移る。拠点をタップすると、自宅 → メイン画面、ゲーム拠点 → ゲーム選択画面 → 各ミニゲーム画面、探索拠点(洞窟・海岸・山)→ 探索拠点の画面(8.6節)へ遷移する。戻る操作は、ひとつ前の画面へ戻る(探索拠点の `この場を離れる` はワールドマップへ)。常時表示のボトムナビゲーションは置かない
- **メイン画面のヘッダー**:左に地図アイコン、中央に拠点名と天気アイコン、右にハンバーガーメニュー(フレンド・設定。図鑑への入り口もここに置く。開発用の項目も置いている)。拠点名(いまは仮に「森」)と天気(いまは仮に晴れ)は、背景・天候システム(10.3節)ができるまでの仮の表示。メニューには開発用の項目も置いている(動作確認用の操作・アニメーション確認)
- **地図**:自宅・ゲーム拠点・洞窟・海岸・山の 5 拠点をアイコンで配置する。アイコンと背景は、本番のドット絵ができるまでの仮の絵(絵文字と色の地形)。名称は、メイン画面の背景の拠点(森・廃屋など。10.3節)と重複しないようにする
- **現在地**:育てているキャラクターの小さいアイコンを表示する。探索に出ている間はその探索拠点(複数の場合は最も早く終わるもの)、終わって成果の受け取り待ちの拠点は受け取るまでそこ、それ以外は自宅
- **探索の状況**:探索中の拠点には「探索中(残り〜)」、終わった拠点には「探索完了!」をアイコンの下に表示する。地図の上部に、探索ポイントと同時探索の数(使用中 / 上限)を表示する
- **未解放の拠点**:グレーアウトして鍵を表示し、タップできない(現状は全拠点が解放済み。将来の拠点追加・解放条件に備えた仕組み)
- **ゲーム選択画面**:3 本のミニゲームを並べ、今日のプレイ回数(使用済み / 上限、残り。2.2節)を表示する
- 拠点間を結ぶ固定のルートは表示しない

### 10.5 図鑑画面
- これまでに進化・出現したキャラクターの一覧を確認できる画面
- **未発見のキャラクター**:名前は「???」、姿はシルエット表示にする(4.3節の各ルートで到達しうる進化先のうち、まだ実際に育てて到達していないもの)

#### 10.5.1 図鑑画面の実装上の取り決め(暫定を含む)
- ヘッダーのメニューから開く。「発見 n / 全体」を表示し、キャラクターを一覧にする。各キャラクターに、図鑑の番号(No.)・名前・進化因子を表示する
- **未発見**は、名前を「???」、姿をシルエットにする。**進化因子は、未発見のものもすべて表示する**(10.5節)

- **発見の判定**:いまの育成の状態から、通ってきた段階をすべて発見済みにする。成熟期は、通常ルート(知力/筋力の優劣。同数は知力ルート扱い)。特別ルートの進化は未実装のため、未発見のまま残る。発見の記録は、アプリを開いたとき・図鑑を開いたときに更新し、世代交代をまたいで残る
- 分岐で選ばなかった進化先を、シルエットのまま残して因子を表示する仕組み(10.5節)は、特別ルートの進化(選択 UI)の実装後に対応する
